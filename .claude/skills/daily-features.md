# Skill: Daily-Use Features

These are user-facing behaviors that compose across the email, calendar, and todo connectors. Each notes which subsystems it touches and any implementation considerations. Build roughly in the order listed — later ones depend on patterns established by earlier ones.

## Morning briefing
One query ("what's my day look like") pulls today's calendar, unread/priority email, and due todos into a single summary. Good first feature to build — it exercises all three connectors in one request and validates the router's ability to fan out to multiple tools and merge results.

**Built 2026-07-13, live-verified.** As built: no tool fan-out — `daemon/llm/briefing.py` assembles the three caches deterministically (`build_sections`: explicit empty + not-connected + still-syncing markers per section) and one fast-model pass narrates it (`compose_briefing`; system prompt forbids padding/invention). `BRIEFING_HINT` (`brief(ing)?`/"my day") is checked **ahead of every other chat route** — "my day" phrasings also match `CAL_HINT`, and the plain path with calendar-only context would otherwise steal them. `briefing.today` is the collected one-shot behind the Dashboard "☀ Briefing" button (busy-guarded, dismissible panel; daemon errors unstick it via `status_requested`). Verified over the real socket: chat + one-shot both named the real event, real unread mail, honest "none due" todos. Residual: the 4B model narrates list-ishly (reproduces every unread line) — acceptable; tighten the system prompt if it grates.

## Commitment tracking
Scans sent email for things you committed to ("I'll send that over Friday") and surfaces them as suggested todos. Reuses the existing `llm-extracted` source pattern from `todo-system.md` — never auto-commits these, always surfaces for confirmation like any other LLM-extracted todo.

**Built 2026-07-13, live-verified.** As built: `daemon/llm/commitments.py::scan` walks SENT mirror rows oldest-first from a `sync_state` cursor (first run bounded to 90 days; ≤20 messages/scan; a failed scan leaves the cursor so it retries), one fast-model extraction per message. **Grounding is mechanical**: an item survives `validate()` only if its `quote` appears verbatim (case/whitespace-normalized) in the body — same rule-class as `book_recs.validate_recs`. Suggestions live in their own `todo_suggestions` table (pending/accepted/dismissed) so `open_todos()` — briefing, chat context — never counts an unconfirmed extraction; an email id present there in ANY status is never re-suggested. Accept promotes via `TodoStore.add(text + ' @due', source='llm-extracted')`; the raw-string reuse keeps one insert path. Surfaces: Todos-screen SUGGESTED section (Accept/Dismiss per row, busy-guarded "Scan sent mail" button) and the `PROMISE_HINT` chat route ("did I promise anyone anything?") which runs the same scan on request — never in the background. Live-verified: 20 real sent messages scanned, one genuine commitment extracted with its verbatim quote, accept produced the `llm-extracted` todo, double-accept errored cleanly.

## Meeting prep
Before a calendar event, pulls any email threads involving the attendees so context is ready without manually digging. Needs attendee emails from the calendar connector cross-referenced against the email connector's search — a natural first use of chaining two MCP tool calls in one router decision.

**Built 2026-07-13, live-verified.** As built: **no MCP chain** — retrieval is deterministic daemon-side (`daemon/llm/meeting_prep.py`), the model narrates one handed-over data block, same grounding pattern as briefing/book-recs. `find_event` resolves "my 2pm" / "the standup" over the cache window (today → +7 days, `PREP_WINDOW_DAYS`): clock times filter (bare "9:30" tries both half-days; a clock time never matches an all-day event), title+attendee-word overlap ranks, soonest-upcoming wins ties; no hit → "I don't see that meeting", **no LLM pass at all**. Attendee history comes from `EmailStore.involving(addr)` (sender/recipients LIKE with escaped wildcards, newest first, 5 per attendee) because the FTS index doesn't cover addresses; each line carries date + direction ("from them"/"from you") + subject so the brief is checkable. Honest markers: no attendees listed / no history with X / mirror unavailable. `PREP_HINT` (`\bprep\b` or `prepare (me) for`) runs ahead of the promise/briefing routes; bare "prepare" deliberately doesn't match ("prepare a speech"). Route only taken when a calendar facade exists. Live-verified over the real socket: title lookup found the event, the brief cited 5 real mirror subjects/dates with correct directions (all cross-checked), no-match answered honestly and instantly. Residual: the 4B narration appended an invented "no email history for Josh Sizemore" line about an attendee that wasn't in the data — an absence claim, harmless, same class as the briefing's list-ish narration; escalation stays closed unless this worsens in real use.

## Inbox triage digest
On request (not a background push), summarizes what's in the inbox and flags what actually needs a response vs what doesn't. Distinct from a notification system — this is a pull, not a push: you ask for it, it doesn't interrupt you.

**Built 2026-07-13, live-verified.** As built: `daemon/llm/triage.py`, `TRIAGE_HINT` ("triage" / "needs a reply|response|answering") checked **after** COMPOSE so "reply to X saying thanks" still opens the compose popup. Rows = unread(15) + recent inbox(15), deduped, capped 20. **Per-message verdicts, not one batch pass**: the first cut sent all 20 numbered messages in one prompt and the 4B fell apart live (newsletters in needs_response, 16/20 uncategorized, hallucinated "why" text) even after prompt sharpening; one tiny `{"bucket", "why"}` JSON verdict per message — the commitments-scan pattern — fixed it completely (20/20 sensible on the same inbox). Grounding is structural: the model only ever picks a bucket + reason; sender/subject/date in the digest are rendered from the mirror rows, so a line cannot misname a message. Unparseable verdict → message honestly counted in a "(didn't categorize N)" trailer, never guessed; no verdicts at all → honest "couldn't triage". Not-connected / empty-mirror answer without waking the model. Cost: ~2.5 min for 20 messages on CPU (model cold) — fine for an explicit pull, shrinks when the iGPU backend lands. No writes: the user acts in the Mail screen.

## Natural-language scheduling
"Find 30 minutes with X this week" checks free/busy via the calendar connector and proposes times rather than you checking manually. Any actual event creation still goes through the write-confirmation flow in `calendar-integration.md`.

**Built 2026-07-14, live-verified.** As built: `connectors/free_slots.py` is pure deterministic math — `parse_duration`/`parse_window` (this/next week, weekend-before-week ordering because "this weekend" contains "this week", weekday names, default next 7 days) and `find_slots` (half-hour-aligned starts inside `[scheduling]` hours, default 8:00–20:00 incl. weekends; today rounds up past now+15 min; all-day and cancelled events don't block; options spread across days before repeating one). **The proposal deliberately skips the LLM** (deviation from the spec's "model phrases it"): `render_slots` emits exact numbered `Thu 2026-07-16 08:00–08:45` lines + the only-your-calendar honesty note — a garbled time in a scheduling proposal is worse than a dry message, and the exact text doubles as machine-usable context. `SLOT_HINT` (find…minutes/slot/time, "when am I free") routes before EVENT_HINT. **Booking follow-up**: `BOOKING_HINT` ("book/take/grab the first one") is taken only when the previous assistant turn contains `SLOT_HEADER`; that turn plus the originating ask ride as `context` into `propose_event`, so "book the second one" resolves to the exact slot and the title keeps its purpose ("Call with Chris"). **Gate change forced by live verification**: the 4B reliably invents an email for "call with Chris" (`chris@example.com`) and prompt steering did NOT stop it, so `validate_proposal` now *drops* attendees the user didn't literally type (message or slot context) instead of refusing the whole event — nothing is ever invited unvetted, the confirm dialog shows exactly what happens, and bookings stop dead-ending. Live-verified end to end twice on the real calendar (create through confirm, then confirm-gated delete cleanup).

## Local knowledge base / notes Q&A
RAG over a local folder of notes/docs so you can ask "where did I write down X." Good candidate for testing the MCP plumbing before tackling Gmail/Calendar, since a filesystem MCP server is the simplest one to stand up. Needs a lightweight local embedding step (small embedding model, separate from the chat model) plus a vector store — SQLite with a vector extension is enough at this scale, no need for anything heavier.

**Built 2026-07-14, live-verified.** As built: `connectors/notes.py` (index/search) + `daemon/llm/notes_qa.py` (narration). Embedding: `nomic-embed-text` via a new `OllamaClient.embed` (keep_alive rides along; benchmark in `llm-serving.md`); vectors in sqlite-vec (`notes_vec` vec0 table, chunk ids joined to `notes_chunks`) inside the existing DB — new dep `sqlite-vec`. Chunks: paragraphs merged to ≤1200 chars. Reindex is mtime-based and runs at the top of every notes question (`~/Documents/Notes`, `[notes]` config, created if absent; .md/.txt only, recursive); a changed `embed_model` wipes and rebuilds the index (model name keyed in `sync_state` — vectors from different models don't mix). `NOTES_HINT` ("my notes" / "where did I write/note/jot" / "notes say") routes ahead of the tool loop, with a negative lookahead so "my notes *folder*" stays with the fs tools. KNN top-4 passages + paths go through one narration pass; grounding: answer only from passages, name the path(s). **No distance threshold** — KNN always returns nearest-k, so "nothing relevant" honesty is delegated to the narration prompt ("say so plainly, never fill from general knowledge") — held up live. Empty folder / zero hits answer without narration. Live-verified: password question answered with the real path + verbatim phrase; unrelated question honestly declined; a line appended to a note was picked up by the next question's reindex. Two starter example notes seeded in `~/Documents/Notes` (named `lumen-example-*`, deletable).

## Japanese study nudge
Surfaces "you haven't done your Manabi SRS reviews today" as a todo-like reminder. Deliberately thin — Lumen should not reimplement any of Manabi's SRS logic, just read a simple signal (e.g. last-review timestamp) that Manabi exposes, and treat it like any other due-today item.

## Quick capture
The hotkey quick-launcher doubles as a scratchpad: free text that isn't clearly a question defaults to becoming a todo or note rather than requiring an explicit "add a todo:" prefix. Router's intent-classification step (from `todo-system.md`) handles this — falls back to "capture as todo" when the input doesn't parse as a question or command.

**Built 2026-07-13, live-verified.** As built: `connectors/capture.py::classify` is the deterministic gate (questions/greetings/assistant-command openers → chat; @date/#tag or ≤8-word fragments → capture; long plain prose → ambiguous → one fast-model TODO/CHAT verdict, model-down falls back to capture — an Undo click beats a lost note). Only the launcher sets `capture_ok`, and only on a thread's **first** turn — mid-conversation you're chatting. A capture answers with a `captured` event (never creates a conversation) and the palette renders "✓ Added todo … — Undo". "email X about Y" deliberately stays chat: the compose route owns it. NL add ("add a todo: X" / "remind me to X") and mark-done ("mark X done", `router.TODO_ADD`/`MARK_DONE`, checked ahead of even the briefing route) work from any chat surface; mark-done fuzzy-matches open todos and lists multiple matches instead of guessing. Live-verified over the real socket: grammar parsed (due+tag), question with capture_ok chatted and cited the just-captured todo, mark-done toggled, undo deleted.
